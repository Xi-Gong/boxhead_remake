# v0.2.6 verification data

Baseline: released v0.2.5 (7ce3aef). Candidate game code: 0af7e6a; later commits add QA and documentation. Production browser probes use headless installed Chrome155.0.8059.84 / Node24.14.1, Intel ANGLE/D3D11, 1280×960 CSS, DPR1, BitmapData scale2, default GL filters and initial seed182026. Baseline/candidate runs alternate; no other tests or builds run during collection.

Reproduce with `GAME_URL=<production preview> PERF_OUT=<report.json> node tests/browser/run-perf-game.ts --release`. PowerShell users set the two environment variables before invoking Node. The real-game probe warms assets on boot, idles the menu, measures transitions, then runs ordinary gameplay, 60 explicit zombie spawns (with a one-second warmup), and a paused scene after a half-second warmup. The high-load fixture asserts all60 spawns succeeded; per-phase world state verifies simulation is advancing/frozen as intended.

`frameP50/P95` are instrumented Player enterFrame+render cost per rendered rAF, not refresh intervals or FPS. `taskMs/scriptMs` are CDP renderer CPU task totals for each phase. Heap samples and sampled allocations/GC include the identical measurement instrumentation; heap differences at a particular phase can reflect GC timing, and are not a retained-memory reduction claim. Cache/object/reference counts describe the live display tree. Every phase has zero attached disposed bitmaps.

The two microbenchmarks load the actual baseline/current functions and check equivalent behavior before timing three warmed runs. Their speedups apply only to the scheduler median and embedded-glyph coverage paths, respectively. They are not whole-game FPS multipliers.

The complete local logs/screenshots remain under `generated/reports/v026` and `generated/reports/qa`. LAN probes use the released v0.2.5 asar and final v0.2.6 unpacked app with the same Electron44.7.0 runtime, native default window/render settings and offscreen/background-throttling flags. The browser viewport above does not describe these native windows. LAN uses real localhost TCP, fixed initial Math.random source0.424242 and the existing host seed formula (seed1822105515). These numeric archives preserve raw frame arrays and CPU/heap/cache/reference measurements; hostnames, local addresses and screenshot paths are excluded.

`*-lan-steady-{1,2,3}.json` are three alternating pairs with30ms one-way delay,20s steering/fire windows, lockstep/audio and display-response checks. `*-lan-reconnect-{1,2,3}.json` are three alternating pairs without injected delay: each retains the original full playtest, including checkpoint transfer to a fresh process, unchanged input delay, concede/resume and the30s timeout. The measured reconnect phase spans the disconnect wait and recovery, so its elapsed time is recorded and CPU totals must not be treated as equal-duration isolated simulation costs. Reconnect host frame-p95 medians are1.0ms for both versions; all attached disposed-bitmap counts are0.

`candidate-lan-delay-{60,100}.json` retain the additional delayed windows, numeric lockstep samples and operation-latency probes. Rollback coordination is enabled, but prediction depth remains0; input delay adapts and the render-only shadow gives immediate display feedback. At100ms one-way delay the host/client display response was25/6ms while simulation followed183/165ms later.
